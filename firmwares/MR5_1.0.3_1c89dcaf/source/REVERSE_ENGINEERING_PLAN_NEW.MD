## 2. Что установлено (конспект; детали — `source/ANALYSIS.md`)

### 2.1 Шифр и контейнер
- SFC-скремблер: блоки 32 Б на смещениях ≡ 2 (mod 32);
  `seed = 0x2BC1 ^ ((bs−2)>>2)`; LFSR `s' = (s<<1) ^ 0x1021`.
  Ключ 0x2BC1 общий для всех 12 моделей. Дешифратор: `source/decrypted/decrypt_all.py`.
- JLFS-записи по 32 Б (`hcrc|dcrc|off|size|flags|rsvd|idx|name[16]`),
  CRC16 poly 0x11021. Инструмент: `tools/jlfs_parse.py`.
- app.bin @ флеш 0x100 → XIP 0x06000100 (точка входа у всех 12 моделей).

### 2.2 CPU и память
- pi32v2, LE, 16-битные слова (инструкции 2/4/6+ байт).
- RAM: sp=0x103840; .data → 0x104840/0x1094E0; BSS 0x105780+0x3D60;
  кандидат в main — 0x06018310.
- Открытый вопрос: дальние `call.xl` вне флеш-окна (ROM/загрузчик/банк?).

### 2.3 Инструментальная база (воспроизведение)
- Таблица инструкций: `jvitkauskas/pi32v2-isa` (TOML + objdump-референс).
- Генератор спеки: `tools/gen_sleigh.py` (конкатенация
  `_gen_p1 + _gen_p2 + _gen_display_pcode + _gen_pcode + _gen_p3`);
  выход `gen/pi32v2_full.slaspec` → установка в
  `Ghidra/Processors/JieLi/data/languages/pi32v2.slaspec` (+ `.sla`).
- Ghidra 12.2 headless: проект `Temp\opencode\ghidra_proj`, программа
  `app_bin_full.bin`; скрипты в `ghidra_scripts/` (StatsDump,
  VerifyDecode, DecompilerSample, A2CreateRam, A4MarkStrings, B4Rename…).
- Верификация декода: `tools/compare_decode.py` (vs `disasm/mr5_app_disasm.txt`),
  `tools/branch_check.py`, `tools/debug_decode.py`.

### 2.4 P-code (B1, первый контур) — что покрыто и что нет
Покрыто **293/1171 форм** (`tools/_gen_pcode.py`): скалярная ALU, ld/st b/h/w
со всеми режимами адресации (`+offset`, `[sp++]`, `[--sp]`, `[++r=n]`, `++=`),
li (u8/neg5/modimm/s16/u32), rmw, sp/usp/ssp, cc→psr, abs/negs/min/max/sat8,
testset/rep/swi (pcodeop), системные no-op'ы.

**НЕ покрыто (фаза 2, влияет на качество декомпиляции):**
1. ⚠️ **Флаги psr из cmp/arith-форм** — условные переходы читают биты
   N/Z/C/V, но пишущих флаги форм семантики нет ⇒ условия в декомпилированном
   C могут быть неверными/потерянными. Это главный дефект точности.
2. SIMD/DSP-семейства (~598 форм): all/any/cmp/sum/alls/anys/cmps,
   `*|*`, `+|+`, `<<<`, `><`, float ftof/ftoi/ftou — pcodeop-заглушки.
3. push/pop с динамическим rmask (попкаунт невозможен в SLEIGH-выражении).
4. d[] 64-битные доступы (псевдо-регистровые пары).
5. Точные семантики testset/rep (сейчас pcodeop).

### 2.5 SLEIGH-гочаи (шпаргалка; полн. список — ANALYSIS.md §8b)
- Один 16-битный LE-токен + `;`-секции; BE-токены байто-свапят слова.
- attach variables несовместимы с attach names на одном поле; attach values
  на names-поле — через компаньон-поле на тех же битах.
- `sext/zext` — только на sized-выражениях: `local t:2 = поле;` затем
  `sext(t)`; truncation — явный `:N`; в `[]` размер писать нельзя.
- `if` только как `if (cond) goto <L>;`; тернарника нет; литералы с размером
  (`0:4`); `local` до использования; display с «голого» поля — префикс `""^`.

## 6. Порядок работ (рекомендация)

1. **B1.2 (флаги psr)** — без него декомпилятор полу-пригоден; самый

4. **B3 (SDK-сигнатуры)** — как только появятся эталонные материалы.
5. **C4 (разметка данных)** — параллельно с чтением декомпила.
6. **B4.2 (ручное именование)** — по мере чтения подсистем.
7. **D2.2** — после стабилизации декомпила.
8. **E** — только по явному запросу владельца устройства.
